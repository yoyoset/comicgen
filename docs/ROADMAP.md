# comic-gen 演进路线图与工作循环

> 本文档定义的是**怎么推进**，不是某个功能怎么实现。功能细节写在 commit message、
> `AGENTS.md` 的「关键设计」和项目 memory 里。
>
> 起因（2026-08-28）：把 comicDPI 的「老漫画高清化」能力并进来，功能从 1 件变成 3 件，
> 界面从 6 个 tab 变成 8 个。**功能增长撞上了界面和代码结构的天花板**——不是先加功能
> 再考虑重构，是加功能这件事本身必须以结构调整为前提，否则每加一个功能，UI 和
> `main_window.py` 都会再臃肿一截，最后没人敢动。
>
> 目标不是"代码干净"，是**一个陌生人能下载、装上、跑出成品、并且愿意推荐给别人**。
> 代码干净是达成它的手段之一，不是目的本身。第一版本文档写成了纯工程整洁度路线图，
> 缺了用户侧的全部验收标准和「首次使用」这条最脆的路径，已修正。

## 一、终点线：v1.0 的定义

没有终点线的路线图会无限延长，永远差一点。**下面这张清单全绿就是 v1.0，可以对外说
"这是一个实用软件"**，剩下的都是 v1.x。

**用户侧（U）**

| # | 门禁 | 怎么验 |
|---|---|---|
| U1 | 陌生人从下载到第一个成品 ≤ 30 分钟，全程无需读文档 | 找一个没用过的人实操，计时，记录他卡在哪 |
| U2 | 任何一次失败都给出「人话原因 + 下一步怎么办」，不出现原始异常字符串 | 故意造 6 类失败（缺模型/缺 GPU/缺 UnRAR/盘满/坏文件/输出被占用），逐条看提示 |
| U3 | 主界面三件事一眼能分清，不需要理解内部阶段 | 见 §2.1 |
| U4 | 每个耗时操作都有进度和剩余时间，没有"卡住不知道在干嘛" | 已基本达成，重构后回归 |
| U5 | README 有截图、有"我该用哪个功能"的决策指引 | — |

**工程侧（G）**

| # | 门禁 | 现状（2026-08-28） |
|---|---|---|
| G1 | 单文件 ≤ 600 行 | ❌ `ui/main_window.py` 974 行 |
| G2 | `core/` `pipeline/` `app/` 零 Qt import | ✅ |
| G3 | `ui/views/` 纯视图：不构造 `Config`/`Runner`，不写文件系统 | 需核 |
| G4 | 每个"分发点"只有一处清册 | ❌ 引擎清单三处硬编码 |
| G5 | 每个"追加写"的文件/目录有上限或清空策略 | ✅ |
| G6 | 新增常量有实测来源或显式标注"未校准" | ✅ 传统良好 |
| G7 | golden-run 回归脚本存在且全绿 | ❌ 不存在，见 §3 |

G1 的意义不是行数，是**行数超标基本等价于"这个文件承担了不止一件事"**。
G4 现在三处违反：`pipeline/registry.py`（权威）vs `ui/workers.py` 下载面板 vs
`ui/views/translate_view.py` 引擎下拉。AGENTS.md 第 8 条当初留话"真要加第三个引擎时
一起改"——`passthrough` 就是第三个。

## 二、目标状态

### 2.1 界面：按「用户想干的事」组织，不是按内部阶段

用户真实想干的事只有三件，界面就该只有三个入口：

```
① 翻译成中文看        日漫 → 中文
② 老漫画看清楚        糊扫描件 → 清晰（AI放大 / 字体精化，可叠加）
③ 塞进墨水屏          任意漫画 → Kindle/iReader 的 CBZ
```

现状 6 个 tab（翻译/批量/校对/设置/模型管理/环境自检）+ 两个新功能 = 8 个平铺 tab。
8 个平铺 tab 不是"功能多"，是**没有分类**——第一次打开无法判断该点哪个。目标收敛成三个区：

```
┌─ 处理 ────────────────────────────────────────┐
│  我要:  (·) 翻译成中文  ( ) 看清楚  ( ) 塞进墨水屏  │
│  ┌ 输入 ─ 列表里 1 项=单任务，多项=队列顺序执行 ──┐ │
│  ┌ 该功能的选项（随上面切换，其余折叠不显示）────┐ │
│  ┌ 输出路径 / 开始·停止 / 进度 / 日志 ─ 三者共用 ┐ │
└──────────────────────────────────────────────┘
┌─ 校对 ─┐  ┌─ 设置（左侧分类：常规/模型/环境自检）─┐
```

三个收敛：

1. **「批量」tab 消失**。它和单任务的唯一区别是"输入列表里有几项"，现在却是两个 tab、
   两套控件、两个控制器共用同一个 `Runner`。
2. **「设置/模型管理/环境自检」合成一个设置区**，左侧分类导航——三者本来就是"配置"和
   "配置的诊断"。
3. **「校对」保持独立**。它是对已有结果的后处理，语义确实不同。

**不要把内部的阶段组合矩阵摊给用户看**。下面这张表是实现视角，不是界面视角。

### 2.2 底层：一条可跳过阶段的链

```
pending → split → upscaled → detected → ocred → translated → rendered → 打包
```

| 用户选的 | split | upscale | detect/ocr | translate | render | 打包出口 |
|---|---|---|---|---|---|---|
| 翻译成中文 | – | – | ✔ | LLM/Sakura | ✔ | 同构输出 |
| 看清楚 · 分格 | ✔ | – | – | – | – | 同构输出 |
| 看清楚 · 分格 + 放大 | ✔ | ✔ | – | – | – | 同构输出 |
| 看清楚 · 仅放大 | – | ✔ | – | – | – | 同构输出 |
| 塞进墨水屏 | 可选 | 可选 | – | – | – | KCC → CBZ |

这张表里没有一格需要新的编排代码——`Runner._run_stage` 已经是回调注入的骨架，缺的
只是"阶段禁用时空转推进状态"和"打包出口分叉"两处。

**`split` 是唯一一个改变页数的阶段**（1 页 → N 格），这是它和其它阶段的本质区别：
`pages.json` 的每页一条记录变成"每格一条 + 记住来自哪一页"。这一点在实现时不能
含糊——断点续跑、校对页定位、失败页报告都建立在"页"这个单位上。

## 三、回归保护（做任何重构之前必须先有）

R3/R4 要拆 974 行的文件、重做整个界面。这个项目**明确不做 UI 自动化测试**
（`QGraphicsScene` 在 pytest 里反复构造/析构会真实触发 access violation，已实测），
验证靠一次性离屏脚本——**用一次性脚本保一次大规模重构等于没保**。

所以重构前先建 `scripts/golden_run.py`：

- 走 `app/job_service.py`（Qt-free CLI 入口）而不是 UI，因此**界面怎么重构它都不受影响**，
  正好卡住"重构不能改变行为"这条。
- 用 `scripts/make_sample.py` 生成的固定素材，跑完整流程，比对：页数、每页
  `pages.json` 的状态与区域数、输出文件尺寸、各阶段是否有 error。
- 结果落 `tests/golden/` 下的基准 JSON，差异即失败。
- 用 `mock` 引擎跑一份（快、确定性，进 CI/每轮门禁）+ 真实引擎跑一份（慢，手动，
  重构前后各一次）。

这是 G7，也是 R3 的前置条件，不是可选项。

## 四、工作循环

每一轮（一个可独立交付的切片）走同一形状。**第 3、5、6、7、8 步不允许跳过**。

```
1. 定范围     写下「这轮做什么」和「这轮不做什么」+ 理由
2. 读现状     AGENTS.md「关键设计」相关条目 + 要改的模块
3. 先结构     这轮要动的地方若已违反 §1 的 G 门禁，先还债再加功能
              （不是加完再重构——加完就没人重构了）
4. 实现       新逻辑优先落在 Qt-free 纯函数；UI 只做壳；机械部分委派（见 §6）
5. 实测       跑真实数据，记录可比较的数字，落进 tests/golden 或 memory
6. 门禁       pytest + golden_run + health_check 三绿
7. 当一次用户  自己从零走一遍这轮碰过的路径，只用界面不看代码。
              卡住/看不懂的地方记下来，进下一轮的范围
8. 收口       单一逻辑一个 commit（message 带实测数字）
              → 同步 AGENTS.md / CHANGELOG / 项目 memory
```

第 7 步是这版新增的，也是最容易被跳过的一步。工程门禁全绿和"好用"之间没有必然联系，
只有真的当一次用户才能发现差距。

**关于实测（第 5 步）**：能实测的不写"应该"；第三方库行为（spandrel / KCC /
PyInstaller+multiprocessing）一律在**本仓库自己的环境**里验，不能引用 comicDPI 的结论
直接当数（两边依赖闭包和打包配置都不同）；新阈值必须有实测来源，做不到就在注释里
明写"未校准的保守起点值"（`REGION_QUALITY_MIN_SCORE` 就是这么处理的）；
**发现假设和实测矛盾时，如实记录"原以为 A、实测是 B"**——这类记录比结论本身更有价值。

## 五、路线图

顺序原则：**能最早证伪的先做；重构之前先有回归保护；结构和界面先立住，新功能才是
"填进去"而不是"挂上去"**。

> **2026-08-28 已推翻一次**：原 R1/R2 是「字体精化」（OCR 原文 → 重画干净字）。
> 实测后作废，见 §5.1。当前主线改为「分格切分 → 逐格 AI 放大 → 墨水屏输出」。

| 轮 | 内容 | 交付判据（可对比的证据，不是感觉） |
|---|---|---|
| **R1** | **分格切分落地**：`pipeline/panel.py`（XY-cut + 格线校验，纯函数、无模型、可离线单测）+ 阅读顺序 + 接进 Runner 的阶段链 | 6 页基准素材切分偏差 ≤3 格且目视全对；单测覆盖 |
| **R2** | **逐格放大**：spandrel + tile 化推理 + OOM 降级，**按每格实际需要的倍率**放大到设备分辨率 | 装 spandrel 前后 `torch.cuda.is_available()` 各验一次；前后对比图 |
| **R3** | **回归保护**：`scripts/golden_run.py` + `scripts/health_check.py` 落地 | G7 绿；health_check 能准确报出当前两条红线 |
| **R4** | **结构债**（机械，可委派）：拆 `main_window.py`；统一引擎清册 | G1/G4 转绿，golden_run 前后一致 |
| **R5** | **界面 A（低风险）**：设置三合一 + 三个功能入口切换 | 第 7 步"当一次用户"记录 |
| **R6** | **界面 B（动控制器）**：输入列表吃掉「批量」tab | golden_run 绿 + 队列场景手测 |
| **R7** | **首次使用路径**：模型下载引导、缺依赖的人话提示、6 类失败逐条过、README 截图与决策指引 | U1/U2/U5 转绿——**找一个没用过的人实操计时** |
| **R8** | **墨水屏转换**：KCC 子进程 + 出口分叉 | 产出 CBZ 分辨率精确等于目标设备 |
| **R9** | **打包**：KCC 是否需拆独立 exe 的实测结论；`bundle_packages.py` 更新 | 冻结 exe 里真跑一次完整流程 |

### 5.1 被推翻的「字体精化」（保留记录，不要重走）

原计划是 OCR 出原文、不翻译、用干净字体重画。2026-08-28 用七龙珠 epub 实测：

| 阶段 | 句级**完全正确**率 |
|---|---|
| manga-ocr 原始（繁体竖排） | ~30% |
| + Qwen3-14B 纠错 | **~40%** |

40% 意味着 10 个气泡有 6 个被画上错字。用户当前体验是"累但看得懂"，重画后变成
"轻松但看的是错的"——**净损失**。且 LLM 会产出"通顺但错误"的句子
（`我国来了` → `我國來了`，正确是 `我回來了`），比乱码更危险，用户读时不会觉得可疑。
根因是 **LLM 看不到图**，只能靠语言合理性猜。

细节见项目 memory `zh-vertical-ocr-feasibility`。要重启这条路，唯一有希望的方向是
**视觉模型（VLM）直接看气泡出字**，把 OCR 和纠错合成一步——但那是独立探索分支，
不进主线。

### 5.2 为什么是「分格切分」

同一格内容在设备上的实际显示倍率（实测 6 页）：

| | Kindle Voyage | iReader SmartX |
|---|---|---|
| 现状（整页塞进屏幕） | 1.41x | 1.83x |
| 分格后（单格塞进屏幕，中位） | 2.58–4.41x | 3.38–5.78x |
| **字体实际放大** | **1.8–3.1 倍** | **1.8–3.2 倍** |

原页里占比越小的格（远景对白）收益越大——**正是用户实际抱怨的那类**。
**零 AI 风险**：确定性算法，不认字不改字，最坏是某页多切/少切一格。

**顺序必须是「先分格、再逐格放大」**，不是整页放大再分格：每格只放大到实际需要的
倍率（大格 1.5x 够、小格要 3.5x），且格比页小、显存友好。所以 R1/R2 是一条链，
不是两个并列功能。细节见 memory `panel-split-feasibility`。

R5/R6 拆开是因为界面重构一次做完最容易烂尾：设置三合一和入口切换是纯视图改动、风险低；
「批量 tab 消失」要动 `JobController`/`BatchController` 的边界，风险完全不同档，
不该塞进同一轮。

R7 排在两个新功能之前：**首次使用路径是这个软件离"实用软件"最远的一块**，且它的问题
会随着功能变多而放大——先修好，R8/R9 加功能时顺手保持，比最后再补便宜得多。

## 六、怎么用 AI 推这件事（分工）

| 大量交给 AI | 必须由人拍板 |
|---|---|
| 机械重构（拆文件、统一清册、改签名） | "糊字重画之后是不是真的更好看" |
| 写测试、golden-run、health_check | 优先级顺序 |
| 把实测结论转成文档 / memory | 阈值定在哪（看真实样本） |
| 一致性检查、文档漂移排查 | "这个界面我第一眼看不看得懂" |

两条具体做法：

1. **R4 这种纯机械重构应该委派**（本仓库可用 `progate`/`flashgate`）：有明确验收标准、
   无架构判断的工作交出去，主线留着做需要判断的部分。委派的前提是 R3 的 golden_run
   已经存在——没有回归保护就委派重构是在赌。
2. **每轮结束交"可对比的证据"，不是一段说明**：前后对比图、准确率数字、门禁报告。
   人的角色固定成"提供真实素材 + 看结果拍板"。

## 七、合并时才暴露的三个冲突（实现时不能漏）

1. **`loader` 的降采样和 AI 放大正面冲突**。`target_long_edge_px(pdf_dpi)` 会把长边超过
   B5 参考值的图先缩小再进流水线（2026-08-22 为解决 LaMa 抹字 4.4 分钟/页加的）。
   高清化模式下这等于"先毁细节、再放大"。`upscale_enabled` 时必须绕开这一层。
2. **磁盘预检系数 ×2.5 会失效**。4 倍放大 = 16 倍像素，`Runner._check_output_space` 会
   严重低估，"跑到一半写满盘"这个已经防住的坑会重新打开。
3. **`cleanup_intermediate` 必须覆盖 `upscaled/`**——全流程体积最大的中间产物。

## 八、这份路线图不做什么

- **不做插件化/多后端抽象**。三件事是已知全集，`Runner` 的阶段链够用。
- **不做 UI 自动化测试**（有实测理由，见 §3），回归保护走 golden_run 这条 Qt-free 路径。
- **不做 EXE 体积瘦身**。comicDPI 评估过（torch/lib 占 3.6GB，无官方支持的低风险排除
  方式），结论不做，这边同样不做。
- **不做 CPU 降级跑 AI 放大**。几百页要几小时，不现实。
- **不做在线更新/遥测/账号**。绿色软件形态是刻意的，不改。
