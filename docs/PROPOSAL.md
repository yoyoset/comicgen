# 漫画自动翻译工具 · 方案讨论稿 v0.1

> 状态：讨论稿，未动工
> 目标：把一个漫画文件夹（或 ZIP/EPUB）丢进去，自动完成「日文定位 → 识别 → 翻译 → 抹字 → 贴回」，输出翻译后的漫画。

---

## 1. 项目目标

**一句话**：日漫生肉 → 熟肉 的全自动流水线。

**核心场景**：
- 用户拖入一个文件夹 / ZIP / EPUB，选择目标语言（默认 日文→简体中文）
- 程序逐页处理，输出同格式的翻译成品
- 中间产物可保存、可人工校对后重新渲染（译后编辑）

**非目标（V1 不做）**：
- 不做实时翻译（屏幕取词式）
- 不做拟声词（SFX）和手写体的完美处理（尽量覆盖，不追求完美）
- 不做上色、修图等图像增强

---

## 2. 整体流水线（Pipeline）

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 输入解包  │ → │ 文本检测  │ → │ OCR 识别 │ → │  翻译    │ → │ 抹字修复  │ → │ 文字渲染  │ → 打包输出
│ (loader) │   │(detect)  │   │  (ocr)   │   │(translate)│  │(inpaint) │   │ (render) │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                    │              │              │
                    └──────────────┴──────────────┴──→ 中间产物 JSON（可编辑、可断点续跑）
```

每个阶段都是**可插拔模块**（接口 + 多实现），通过配置文件切换。

### 2.1 输入解包（Loader）
| 格式 | 处理方式 | 优先级 |
|---|---|---|
| 文件夹 | 扫描图片，**自然数排序**（`1.jpg, 2.jpg, 10.jpg` 而非字典序） | V1 |
| ZIP / CBZ | 本质相同，解压到临时目录后按文件夹处理 | V1 |
| EPUB | 也是 ZIP，但要解析 OPF  spine 确定页面顺序，输出时需保序重打包 | V1 |
| PDF | 需先渲染成图片（pymupdf），排版信息丢失风险 | V2 |
| RAR / CBR | 依赖 unrar，边角格式 | V2 |

**输出格式**：默认与输入同构（文件夹→文件夹，ZIP→ZIP，EPUB→EPUB），另可选导出 PDF、纯译文文本。

### 2.2 文本检测（Detection）
检测图片中的文字区域（气泡内文字 + 气泡外旁白），输出：区域框 + 掩码（mask）+ 横排/竖排方向。

| 方案 | 说明 | 评估 |
|---|---|---|
| **ogkalu/comic-text-and-bubble-detector** | RT-DETRv2 漫画文本/气泡检测，1.1 万页语料微调，**Apache-2.0**（规避 GPL 风险），transformers 直接加载 | ⭐ **已实现并选用** |
| comic-text-detector | YOLOv8 + DBNet，能生成掩码，BallonsTranslator 在用（GPL） | 备选 |
| manga-image-translator 自研检测器 | DBNet 系，漫画语料训练，成熟稳定 | 备选 |
| PaddleOCR det | 通用检测，漫画竖排/花体字效果一般 | 不推荐 |
| 多模态 LLM（GPT-4o 等）出框 | 一次调用同时给框+文字+翻译，但框是像素级估计，**不够精确，无法支撑抹字** | 不推荐单独用 |

### 2.3 OCR（日文识别）
对检测出的每个文本块裁剪后识别，需原生支持**竖排**。

| 方案 | 说明 | 评估 |
|---|---|---|
| **manga-ocr** | TrOCR 在漫画语料上微调，竖排友好，本地可跑，业界事实标准 | ⭐ 首选 |
| PaddleOCR（日文模型） | 通用效果好，竖排需额外处理 | 备选 |
| Google Vision API | 日文手写/花体最强，但收费 + 需网络 | 可选云端兜底 |
| 多模态 LLM | 质量高但贵且慢，适合作为「校对通道」而非主通道 | 可选 |

### 2.4 翻译（Translation）
关键诉求：**上下文一致性**（角色名、人称、语气），最好按「整页/整章」带上下文喂给模型。

| 方案 | 成本 | 质量 | 说明 |
|---|---|---|---|
| **DeepSeek API** | 极低（约 ¥1-2 / 千页级） | 好 | ⭐ V1 默认，性价比之王 |
| GPT-4o / Claude API | 中 | 很好 | 可选，支持术语表 |
| **Sakura-13B（本地）** | 免费（需 8G+ 显存） | 中上 | 专为 galgame/轻小说微调的日→中模型，隐私好 |
| Google / DeepL | 免费/订阅 | 中 | 传统机翻，做基线对照 |
| NLLB / Sugoi（本地小模型） | 免费 | 一般 | 兜底 |

**一致性机制**：维护一个「术语表/角色名表」，每章翻译时作为上下文注入；同一文件内缓存已有译名。

### 2.5 抹字修复（Inpainting）
用检测阶段的掩码抹掉原文，修复背景。

| 方案 | 说明 | 评估 |
|---|---|---|
| **LaMa (big-lama)** | 修复质量与速度平衡最好，主流选择 | ⭐ 首选 |
| PatchMatch | 快，复杂背景有残影 | 备选（CPU 场景） |
| SD Inpainting | 重，需要大显存，对纯色气泡背景是杀鸡用牛刀 | 不推荐 |

注：漫画文字大多在白色气泡内，**掩码膨胀 + 简单填充**就能解决 80% 的情况；LaMa 处理气泡外的文字。

### 2.6 文字渲染（Render）
把译文写回图片。**这是最容易被低估、最影响观感的环节**：
- 竖排 vs 横排（日漫多为竖排，中文排版习惯横排，需策略：保留竖排 or 改横排）
- 自动换行 + 字号自适应缩小，确保文字不溢出水泡
- 字体：需可商用中文字体（思源黑体/站酷系等），支持字体包替换
- 描边：气泡外文字需白字黑边等效果，需从原图取色
- 对齐：在气泡内居中

## 3. 关键设计：中间产物与译后编辑

每页生成一个 `xxx.json`，记录全部中间结果：

```json
{
  "image": "page_001.jpg",
  "regions": [
    {
      "bbox": [x, y, w, h],
      "direction": "vertical",
      "source_text": "……なにこれ",
      "translated_text": "……这是什么",
      "font_size": 24,
      "color": [0, 0, 0]
    }
  ]
}
```

**收益**：
1. **断点续跑**：翻译做完后改渲染参数不用重跑 OCR
2. **人工校对**：改 JSON 里的译文 → 只重跑渲染阶段 → 出最终图
3. **缓存复用**：同一页换翻译引擎不用重检测
4. 未来可做校对 GUI / Web 界面

## 4. 技术栈建议

- **语言**：Python 3.10+（CV/OCR/LLM 生态最全）
- **图像**：OpenCV + Pillow + numpy
- **推理**：PyTorch + CUDA（本机 6G+ 显存，检测/OCR/抹字全部本地跑）
- **打包**：zipfile + ebooklib（EPUB）+ pymupdf（PDF，V2）
- **界面**：GUI 选型见 §6.1（待定）
- **依赖管理**：uv / pip + venv

### 4.1 建议的项目结构

```
comic-gen/
├── comic_gen/              # Python 包
│   ├── pipeline/           # 流水线各阶段（全部可插拔）
│   │   ├── loader.py       #   文件夹 / ZIP / EPUB 解包
│   │   ├── detect.py       #   文本检测（comic-text-detector）
│   │   ├── ocr.py          #   OCR（manga-ocr）
│   │   ├── translate.py    #   翻译（DeepSeek / Sakura 可切换）
│   │   ├── inpaint.py      #   抹字（LaMa）
│   │   └── render.py       #   译文渲染
│   ├── core/               # 数据模型（Page/Region）、配置、缓存、任务调度
│   └── ui/                 # 界面层
├── models/                 # 模型权重（git 不跟踪）
├── docs/
└── pyproject.toml
```

## 6. 三种实现路线对比

| 路线 | 描述 | 工作量 | 可控性 | 评估 |
|---|---|---|---|---|
| A. 完全自研 | 所有模块自己写（模型权重可复用开源的） | 大（4-6 周） | 最高 | 长期最优 |
| B. 套壳二开 | 直接 fork manga-image-translator，加 EPUB/格式支持与定制 | 小（1 周） | 低，受 GPL 约束 | 验证需求最快 |
| **C. 混合（推荐）** | 自研模块化框架 + 复用开源模型权重（detector/manga-ocr/LaMa）+ 翻译走 API | 中（2-3 周出 MVP） | 高 | ⭐ **已选定** |

### 6.1 界面层架构（✅ 已选定 Gradio）

核心约束：**流水线必须是 Python**（PyTorch / OpenCV / manga-ocr 都在 Python 生态）。

| 方案 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **Gradio** | 纯 Python，起一个本地 Web 页 | 最快出活（拖文件上传、进度条、前后对比预览都现成），单语言 | 界面是网页风格，定制上限低 |
| Dear PyGui | 纯 Python，原生即时模式 GUI（类似 egui 的手感） | 原生窗口、单语言、性能好 | 组件生态较小 |
| Rust + egui | Rust 前端 → 子进程调用 Python 流水线 | 原生体验最好 | 双语言、双工具链、打包分发麻烦，IPC 增加复杂度 |

分析：egui 本身是 Rust 库，但我们的核心在 Python。若用 Rust+egui，等于「Rust 壳 + Python 内核进程」，界面上选个路径后还是要调 Python，徒增一倍复杂度，**只有在做正式桌面产品时才值得**。

**结论：MVP 用 Gradio**（本地 Web 页），流水线与界面同语言；将来若做正式桌面产品再评估 Rust+egui 壳。

## 7. 难点与风险

| 难点 | 风险 | 对策 |
|---|---|---|
| 竖排文字的检测与渲染 | 中文竖排观感差，横排可能装不进气泡 | 提供排版策略选项；字号自适应 |
| 气泡外文字/拟声词 | 艺术字 OCR 差、抹字难 | V1 尽力而为；掩码膨胀 + LaMa |
| 抹字留残影 | 复杂背景修复不净 | LaMa + 掩码膨胀；极端情况留待人工 |
| 翻译一致性 | 同一角色名前后不一 | 术语表 + 整页上下文翻译 |
| 文字溢出气泡 | 译文普遍比日文长 | 字号自适应 + 最大行数约束 |
| GPU 依赖 | 无 GPU 用户跑得慢 | 检测/OCR/抹字都支持 CPU；也可选全 API 化 |
| 格式边角 | EPUB 各家打包习惯不同 | 按 OPF spine 解析，宽容处理 |
