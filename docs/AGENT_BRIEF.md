## 2. 总目标

把 comic-gen 从"能跑通的 demo"推到"可以放心交给别人用的成熟软件"。

四条成熟度判据，每完成一件待办都对照一下自己推进了哪条：

1. **可靠**：493 页的真实任务从头跑到尾不出幺蛾子；中断能续；失败可诊断且不伪装成功。
2. **可规模化**：一次扔进 20 卷，睡一觉回来全部处理完，不需要人盯着点确认框。
3. **可信任**：用户能一眼看出哪里翻错了，并快速改掉；软件不会悄悄产出错误结果。
4. **可交付**：装了就能用，更新方便，依赖明确。

**当前位置**：1 基本达标，3 有校对界面但依赖人工通读，2 和 4 明显不足。

### 4.2 验证纪律（最重要的一条）

本项目有过血的教训：**一整套 pytest 从写出来就没跑过**，因为 venv 里根本没装 pytest，
里面引用着已删除的类。"写了测试"不等于"测试跑过"。

所以：

```bash
.venv/Scripts/python.exe -m pytest tests/ -q
```

- 每轮提交前必须跑，**并把真实输出粘进报告**（形如 `312 passed in 99.63s`）。
- 不允许写"测试应该能过""逻辑上没问题"。没跑就是没验证。
- 基线：**312 passed**。低于这个数说明你弄坏了东西，先修好再说。
- 涉及外部工具/库的具体行为，能实跑验证的不要凭文档或记忆假设。
- 发现自己早先的假设和实测矛盾时，**如实在报告里写"最初以为是 A，实测发现是 B"**，
  不要掩盖这个修正过程——这类记录是排查同类问题最有价值的线索。

### 4.3 真实素材（可直接用来测量）

一次 493 页杂志的完整运行结果就在磁盘上，是校准和验证的金矿：

- 工作目录：`E:\某漫画杂志\某漫画杂志_translated\`

  - `job.json`（完整 Config 快照 + 各阶段耗时）
  - `run.log`（带时间戳的告警）
  - `pages.json.bak-preecho-fix`（修复前的备份，可做前后对比）
- 原图：同目录下 `..\某漫画杂志\`（493 张 JPEG）

**只读它们，不要覆盖写。**需要改动就先复制一份到你自己的临时目录。

### 4.5 环境陷阱（踩过的，别再踩）

- **平台**：Windows 11 + PowerShell 5.1。`&&`/`||`/三元运算符**不可用**。
- **Python**：`.venv\Scripts\python.exe`，3.13。
- **PowerShell 5.1 会把原生程序的 stderr 当成终止性错误**：`$ErrorActionPreference="Stop"`
  的脚本里，PyInstaller 往 stderr 打的 INFO 日志会让脚本在第一行日志处就中止退出。
  跑 `scripts\build_exe.ps1` 请用 `powershell.exe -NoProfile -Command ".\scripts\build_exe.ps1"`
  这种子进程形式。（实测踩过，构建根本没开始就"失败"了。）
- **写 .ps1 脚本若含中文**，必须用 PowerShell 自己的 `Out-File -Encoding utf8`（带 BOM），
  通用文本写入工具产出的无 BOM UTF-8 会被当 GBK 解析导致 parser error。
- **控制台中文显示乱码是显示问题**，日志文件本身 UTF-8 正常，**不要为此改代码**。
- **Qt 测试**：`QGraphicsScene`/`QGraphicsView` 这类对象在 pytest 里反复构造/析构会真实
  触发 access violation 崩溃（试过）。验证 UI 改动用一次性离屏脚本
  （`QT_QPA_PLATFORM=offscreen` 构造真实 `MainWindow` 走一遍流程），**不要往 `tests/`
  里加构造 `QGraphicsScene` 的用例**。
- **重新打包前必须先关掉正在运行的 `comicgen-ui.exe`**，否则文件锁会让换件半途失败。

## 5. 待办队列（按顺序做，不要跳）

### T1. 区域质量测量工具（只读，**做完必须停下来等主脑决策**）

**问题**：上游检测/OCR 产出的区域质量没有任何过滤，这是目前最大的算力+质量杠杆。

**实测证据**（来自 4.3 那次运行）：
- 6127 个检测区域里，**OCR 返回空字符串的是 0 个**——manga-ocr 没有置信度门槛也从不
  返回空，所以杂志上的花纹、logo、装饰框全都被幻觉成日文，照样进翻译和渲染。
- 检测分数分布：`<0.4` 占 7.0%，`<0.5` 占 13.4%，`<0.6` 占 20.8%，`<0.7` 占 30.2%。
- 阶段耗时：detect 111s / ocr 1748s / translate 2158s / render 585s。OCR 和翻译占 85%，
  而它们的成本与区域数成正比。

**要做的**：扩展 `scripts/diagnose_page.py`（已存在的只读诊断脚本），或新增一个只读的
批量统计脚本，从 `pages.json` 产出一份决策报告，至少包含：

1. 区域数/面积/长宽比/检测分数的分布（整体 + 分位数）。
2. 按 score 分桶，每桶抽样若干区域的 OCR 原文与译文，**便于人眼判断"这个分数段是不是
   大多是垃圾"**。这是报告的核心，不要只给数字。
3. 各候选过滤规则（score 阈值、最小面积、极端长宽比）如果启用，分别会砍掉多少区域、
   砍掉的那些里有多少是"看起来确实是垃圾"的。
4. 按当前每区域平均耗时折算，各规则能省下多少秒。

**验收**：
- 脚本**纯只读**，不写 `pages.json`，不改任何图片。
- 能对着 4.3 的真实数据跑出完整报告，报告贴进你的工作报告里。
- 新增的纯函数（分桶、统计、规则模拟）有离线测试。

**做完后**：**不要自己决定任何阈值，不要改 `detect.py`/`ocr.py`。** 把报告交给主脑，
等阈值决策下来再做 T2。这是硬要求——理由见第 3 节第 5 条：这次杂志数据是唯一实测样本，
阈值对正常漫画气泡未必合适。

### T3. pages.json 写放大

**问题**：`Runner._save_pages` 每次都重写整份 JSON，而四个阶段各自逐页调用它
（`runner.py` 有 7 处调用点）。

**实测证据**：493 页的 `pages.json` 是 3.05MB。四阶段逐页落盘 ≈ 493 × 4 × 3MB ≈ **5.8GB
无谓写入**。

**关键约束（不要搞反）**：逐页落盘是**有意为之**，修过一个真 bug——翻译阶段原先
`_save_pages` 在循环外，崩溃/断电/强杀会丢掉整个阶段的译文（200 页 × ~10s/页 ≈ 35 分钟
推理作废）。所以：

- **绝不允许**改成"最后统一存一次"或"每 N 页存一次"来省 IO——那是倒退回已修复的 bug。
- 正确方向是**降低单次写入的成本**，同时保持"崩溃最多丢一页"的保证。

**验收**：
- 493 页规模下总写入量显著下降（给出实测数字，前后对比）。
- "崩溃最多丢一页"的保证有测试守着；`tests/test_runner.py` 现有的逐页落盘断言仍然绿。
- 中断后重跑能正确从断点续，不重做已完成的页。

**这一项如果你判断需要改变磁盘格式（比如拆成多文件），先升级给主脑**——`pages.json`
同时被 `app/review_session.py` 和 `core/job.py` 的 `load_pages`/`save_pages` 读写，
格式变更影响面超出单个任务。

### T5. 批量队列

**问题**：`JobController.start` 明确拒绝并发，没有队列、没有多选。20 卷就是手动跑 20 次、
盯 20 次弹窗。这是"可规模化"这条判据的主要缺口。

**注意一个已知陷阱**：文件夹输入是**递归**的，指向系列根目录会把所有卷当成一个巨型任务、
共用一个 `pages.json`。队列的语义必须是"N 个独立任务各自有独立工作目录"，不是"一个大任务"。

**验收**：
- 能一次加入多个输入，顺序执行，中途失败不影响后续任务。
- 每个任务有独立工作目录和独立 `job.json`。
- 能看到队列进度，能取消单个任务和整个队列。
- 应用层（`app/`，Qt-free）有端到端测试覆盖排队逻辑，用 `translator="mock"` +
  `tests/sample.zip`（两者都已存在）。

**开工前先升级给主脑**：队列该放在 `app/` 层还是 `ui/` 层、失败任务是否自动重试——
这两个是架构决策。

## 7. 什么时候必须停下来升级

命中任何一条，立刻停，写升级请求，不要往下做：

1. 需要定一个**阈值/常量**，而手里没有真实数据支撑。
2. 需要**新增依赖**，或改动 `pyproject.toml` 的依赖。
3. 需要改**磁盘数据格式**（`pages.json`/`job.json`/`settings.json`）。
4. 需要改**分层结构**，或改动第 3 节列的七处资产。
5. 一件事做了两轮还没做完 —— 说明任务被低估了，需要重新拆。
6. 测试从 312 掉下来且你**没有立刻定位到原因**。
7. 你发现本简报或 `AGENTS.md` 与代码实际行为矛盾 —— 报告矛盾点，不要自己改简报。
