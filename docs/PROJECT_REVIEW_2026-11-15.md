# comic-gen 项目评估与改进方案（2026-11-15）

> 评估对象：`main` 分支 78dc46a + 当时工作区的未提交改动。
> 方法：实跑测试和门禁、通读 `pipeline/runner.py` 等核心模块、对照 README / HANDOFF / AGENTS / ROADMAP 与代码现状。
> 标注约定：**【实测】**= 本次评估跑出来的结果；**【读码】**= 只读了代码，没有运行验证；**【文档】**= 引自项目已有文档的数字，本次未复验。

## 0. 一页结论

**项目现在是什么水平**：一个内核扎实、工程纪律明显高于同类个人项目的本地漫画翻译工具。断点续跑、原子写盘、失败不静默、参数锁定加测试守护，这些在 9,566 行产品代码里都是落到实处的。

**最大的三个问题不在代码质量，而在"方向和收口"**：

1. **产品和实际工作分叉了。** 11 月 6 日之后的主要精力花在「繁体中文漫画 → 简体重排」上，这条线完全跑在脚本、定时任务和人工看图上（`scripts/` 下 55 个脚本里 29 个是 `_` 开头的一次性脚本，根目录另有 10 个；这 39 个全部含写死的盘符路径），产品界面里没有它。`pipeline/proofread.py`（195 行，有测试）在 `comic_gen/` 内没有任何调用方。
2. **路线图没有被执行，也没有被修订。** `docs/ROADMAP.md`（2026-08-28）定的 R1–R9 里，R1 分格、R2 放大、R3 回归保护、R4 结构债、R8 墨水屏都没有动工；它定的门禁反而在恶化（`main_window.py` 974 → 1,139 行，界面 6 → 7 个页签）。
3. **已修好的用户可见问题没有发出去。** v0.4.2 之后有 10 个提交，其中「成品 `.jpg` 实际是 PNG、部分阅读器拒读」这个修复至今只在源码里；工作区还挂着 6 个改动文件和 58 个未跟踪项，当前 `ruff` 门禁是红的。

**建议的顺序**：先收口（一周内）→ 发 0.4.3 → 建回归保护 → 决定中文重排这条线要不要产品化 → 再谈新功能。详见 §4。

### 1.3 做得好、应当保持的

- **断点和落盘**：四阶段逐页 try + 逐页写 `pages.json`，状态文件和成品图都走原子写；`_run_stage` 把四份循环收成一份。

- **Qt-free 分层**：`core/` `pipeline/` `app/` 不依赖 Qt，CLI 和 UI 共用同一套流水线。

## 2. 技术角度

按"影响 × 修复成本"排序。每项给出依据和做法。

### T1. 工作区没有收口，门禁是红的 —— 高优先，半天

**依据**【实测】：`render.py` 的 `FORCE_BLACK_TEXT`、`retext_volume.py`、两个测试文件、AGENTS / CHANGELOG 共 6 个文件已改未提交；ruff 报 1 个错误；`docs/AUDIT_WORKFLOW.md`（751 行，AGENTS 第 30 条指向它）、`docs/VISION_OCR_BENCHMARK.md`、`scripts/apply_review.py` 等 11 个被文档引用的正式脚本、两个测试文件都未入库。

**风险**：AGENTS.md 已提交的版本将来会指向一个仓库里不存在的文档；换机器或工作区出事就丢。

**做法**：
1. 删掉 `_stroke_for` 那个未使用导入，ruff 转绿。
2. 分三个提交：(a) `FORCE_BLACK_TEXT` + 两个测试 + AGENTS 第 31 条；(b) 审计流程文档与正式脚本 + `test_audit_diff.py` / `test_retext_masthead.py`；(c) CHANGELOG。
3. 入库前按 HANDOFF §7 扫一遍这些文件里的真实素材路径（仓库是公开的）。

### T2. 一次性脚本堆在仓库里 —— 高优先，半天

**依据**【实测】：根目录 10 个（`apply17.py`、`check17.py`、`scan62_dark.py` …），`scripts/` 下 29 个 `_` 开头，这 39 个全部含盘符路径。按同一个粗略正则（`[A-Z]:[\\/]`），其余 26 个正式脚本里也有 14 个命中——可能只是字体路径或注释里的示例，入库前需要逐个看（见 T1 第 3 步）。另有 `0122/`（1.2 MB 截图）、`AUDIT_DECISIONS.md.bak-*`、根目录 `memory/`、`__pycache__/`、`settings.json`。

**做法**：
- 卷号专用脚本（文件名带 `17` / `22` / `62` / `b12` 的）移到仓库外的工作目录，或 `.gitignore` 加 `scripts/_*.py`、`/*17.py` 这类规则，让 `git status` 回到只显示真正待处理的东西。
- 其中重复出现的动作（裁图核对、补框、合并、暗页扫描）说明有 3–4 个通用工具还没被提炼出来。**只提炼已经重复写过三次以上的**，其余不动。

### T3. 发布滞后 —— 高优先，一天

**依据**【实测】：v0.4.2 之后 10 个提交未发布，其中用户可见的有：
- `56f1c29` 成品页按后缀写 JPEG（此前 CBZ 里是"扩展名 jpg、内容 PNG"，部分阅读器拒读，体积约 3 倍）
- `d3ca58f` EasyOCR 把句点认成冒号/分号（一卷里 296 / 2,356 个区域受影响）
- `44da89e` 译名表、`fff51e2` CLI 字号与 DPI 参数

**做法**：T1 收口后发 0.4.3。发布检查单照 HANDOFF §3，另加一条：`FORCE_BLACK_TEXT` 改变了所有用户的成品观感（彩色字、白字描边都没了），要在发布说明里写明，并考虑是否做成设置项（见 U6）。

### T4. 没有端到端回归保护 —— 高优先，1–2 天

**依据**：ROADMAP §3 把 `scripts/golden_run.py` 定为"重构前必须先有、不是可选项"，至今不存在【实测】。现有 488 个测试以纯函数为主，唯一的端到端用例是 `test_run_job_on_real_sample_zip_end_to_end`（mock 引擎）。

**做法**：按 ROADMAP §3 原设计落地，走 `app/job_service.py`，用 `make_sample.py` 的固定素材，比对页数、每页状态与区域数、输出尺寸、是否有 error。mock 版进日常门禁，真实引擎版在发布前手动跑。这是 T5、T6 的前置条件。

### T5. `main_window.py` 持续膨胀 —— 中优先，2–3 天，依赖 T4

**依据**【实测】：1,139 行、72 个方法，同时管着单任务、批量、模型下载、扫描、组件、诊断、校对、关窗收尾八件事。ROADMAP 定的上限是 600 行。文件头自称"组合根：只接线，不含业务决策"，但 `_on_start`、`_models_not_ready_message`、`_batch_prepare`、`_on_review_export` 都有决策逻辑【读码，按方法名与行数判断】。

**做法**：按职责拆成每块一个协调器（批量、模型/组件、校对），`MainWindow` 只留构造和信号接线。纯机械重构，有 T4 之后可以委派。

### T6. 引擎清单三处硬编码 —— 中优先，半天

**依据**【实测】：`pipeline/registry.py` 是权威，但 `ui/views/translate_view.py:17` 的 `_ENGINES`、`ui/workers.py:170-175` 的 `if key == "sakura" / "llm"` 各有一份。AGENTS 第 8 条和 ROADMAP G4 都记着这笔债。

**做法**：给注册表条目加显示名和"预热工厂"两个字段，两处 UI 从注册表推导。若近期不加第三个引擎，可以继续留着，但要在 T5 拆文件时一并处理，不要单独开一轮。

### T7. 显存余量：阶段之间不释放模型 —— 中优先，需先实测

**依据**：`Runner` 四个引擎缓存只在「暂停」时清空【读码，`release_models` 唯一调用点在 `_wait_if_paused`】。流水线是"全部页检测 → 全部页 OCR → 全部页翻译 → 全部页渲染"，进入翻译阶段时检测和 OCR 模型不再需要但仍占显存。HANDOFF 记录的峰值是 11,850 MiB / 12 GB【文档】，README 也写"余量很小"。

**做法**：先量再改。在一次真实任务里分别记录检测、OCR 模型各占多少显存；如果合计达到几百 MiB 以上，就在 OCR 阶段结束后丢掉这两个缓存。单任务和批量共用 Runner，跨任务复用的收益要一并权衡（批量队列里每卷会多一次检测模型加载）。**收益未实测，不要直接当结论。**

### T8. 状态文件没有版本号 —— 中优先，半天

**依据**【实测】：`pages.json` 和 `settings.json` 都没有 schema 版本字段，只有 `job.json` 记了 `app_version`。`_load_pages` 读失败时记一条日志后按全新任务处理【读码】——对一个跑了几小时的 493 页任务，升级版本后静默重跑的代价很高。ROADMAP 的「分格」会把"每页一条"改成"每格一条"，届时必然破坏兼容。

**做法**：两个文件各加 `schema_version`；读到更高版本时明确报错而不是丢缓存；读到旧版本时迁移。在做分格之前完成。

### T9. 测试耗时集中在两个用例 —— 低优先，1–2 小时

**依据**【实测，`--durations`】：`test_is_model_cached_respects_model_dir` 38.1 秒、`test_ja_factory_passes_force_cpu_to_manga_ocr` 30.0 秒，两条占总耗时的约三分之一。前者很可能扫了本机真实的模型缓存目录，后者很可能真的导入了重型依赖【推断，未打开用例确认】——如果属实，这两条违反了"不依赖外部可变状态"的测试纪律，在别的机器上耗时和结果都可能不同。

**做法**：确认原因后把缓存根指到 `tmp_path`、把重型导入打桩。

### T10. 依赖声明的缺口 —— 低优先，1 小时

**依据**【实测】：`pipeline/proofread.py` 和两个测试文件用到 `zhconv`，但 `pyproject.toml`、`requirements-lock.txt`、`bundle_packages.py` 里都没有它。当前之所以没出问题，是因为 `proofread.py` 没被产品调用、`.venv` 里恰好装着。`zhconv` 还会触发 `pkg_resources` 弃用警告。按 HANDOFF §2 的步骤重建 `.venv-cpu` 后，`test_proofread.py` 是否还能通过没有验证。

**做法**：要么把它加进一个 optional 依赖组并在测试里 `importorskip`，要么等 D1 决策后随产品化一起进主依赖和打包清单。

### T11. 其它小项

- **没有 CI**。测试本来就是离线纯函数，接一个 Windows runner 跑 `ruff + mypy + pytest` 成本很低，能防住 T1 这类"本地红了没发现"。torch 等重依赖的安装时间是主要成本，需要缓存。
- **字体默认值是 Windows 绝对路径**（`Config.font_path`、`AppSettings.font_path`、`render.py` 兜底列表）。项目只支持 Windows，目前不是问题，记录在案即可。
- **`Runner._cleanup_kind`** 是 `_run_body` 里设置、`run()` 里用 `getattr` 读的隐式实例状态【读码】，改成从 `_run_body` 返回更稳。
- **`ui/` 整体不在 mypy 范围内**，这是有意的决定；T5 拆出来的协调器如果不直接碰 Qt 枚举，可以纳入检查。

## 3. 用户角度

以"一个陌生人下载安装包、想翻一本漫画"的路径走查。除特别标注外均为【读码 + 文档】，**本次没有启动真实窗口操作**。

### U1. 第一眼：7 个页签，分不清该点哪个 —— 高优先

**依据**【实测】：`翻译 / 批量 / 校对 / 设置 / 模型管理 / 组件 / 环境自检`。ROADMAP §2.1 在 6 个页签时就判定为"没有分类"，之后又加了「组件」。

**做法**（ROADMAP R5，低风险的那一半）：「设置 / 模型管理 / 组件 / 环境自检」合成一个设置区，左侧分类导航。主界面剩 `翻译 / 批量 / 校对 / 设置` 四项。「批量并入翻译」（R6）要动控制器边界，放后面。

### U2. 跑的过程中看不到任何成品 —— 高优先

**依据**【读码】：阶段是按"全部页"推进的，渲染在最后一个阶段，预览列表读的是 `translated/` 目录。一卷 200 页的书，用户要等检测、OCR、翻译全部跑完才看到第一张译图；如果引擎选错、字体不合适、方向不对，要到最后才发现。

**做法**（二选一，先做便宜的）：
- **便宜**：开始前提供「试跑前 3 页」按钮，走同一条流水线，几十秒出结果，满意了再跑全卷。断点机制保证这 3 页不会重跑。
- **彻底**：改成逐页走完四个阶段。代价是翻译模型和抹字模型要同时驻留显存，在 12 GB 卡上已经没有余量（见 T7），需要实测后才能决定，不建议现在做。

### U3. 显存不足时用户得到什么 —— 高优先，需实测

**依据**：默认配置在 12 GB 卡上峰值 11.85 GB【文档】，8 GB 卡跑默认配置大概率不够。代码里没有显存预检【实测，全库搜索无 `mem_get_info` / `total_memory`】。失败时用户看到的是 llama.cpp 或 torch 的原始错误还是人话提示，没有验证过。ROADMAP U2 列的 6 类失败里也没有"显存不足"这一项。

**做法**：
1. 先在真实环境造一次显存不足，看现在的报错长什么样。
2. 开始任务前读一次可用显存，低于所选引擎的实测需求时给出明确选择：换小模型 / 改 CPU / 仍然继续。
3. 首次运行弹窗按显存大小决定默认勾选哪个翻译模型，而不是一律 Sakura-14B。

### U4. 首次使用要下 12.1 GB —— 中优先

**依据**【文档】：模型约 9.0 GB + GPU 组件约 3.1 GB，装完占盘约 15 GB。README 的"懒得自己点？把这段话贴给 AI 助手"说明作者自己也觉得这一步重。

**做法**：
- 提供一个小模型档位（7B 级 GGUF）作为"先试试看"的选项，把首次下载降到 5 GB 左右。`llm` 引擎已经支持任意 GGUF，缺的只是 manifest 里一条记录和弹窗里一个选项。**翻译质量差多少需要用含退化输入的素材实测**（AGENTS「变更治理」第 2 条）。
- 模型下载有没有断点续传、镜像回退，本次没有核对；GPU 组件有，模型下载走的是 HF 库自带逻辑。国内用户不设镜像时 HF 的可达性是首次体验的最大变数，建议专门测一次。

### U5. 已有能力没有接到界面上 —— 中优先

| 能力 | 现状 | 用户的代价 |
|---|---|---|
| 译名表 | 只有 CLI `--glossary`，README 没提 | 人名乱译只能逐个气泡手改 |
| 字号上下限、检测阈值 | 设置页有 | — |
| 拖拽文件到窗口 | 没有【实测，无 `setAcceptDrops`】 | 每次走文件对话框 |
| 校对修改 → 交付物 | 必须点「导出全部」，重跑全部页的抹字渲染 | 改一个字要等整卷重渲染 |
| 自定义输出路径 | 「导出全部」会忽略，写到默认位置（README 自己写了这条注意） | 交付物出现在意料之外的地方 |

**做法**：译名表接进翻译页（一个"选择译名表文件"的入口就够，不必做编辑器）；加拖拽；「导出全部」改成只重渲染状态被打回 `translated` 的页，其余直接用现成的图重新打包；导出沿用 `job.json` 里记录的输出路径。最后两条都是把已有信息用起来，不需要新机制。

### U6. 「纯黑实心字」是全局写死的 —— 中优先，需要你决定

**依据**：`FORCE_BLACK_TEXT = True` 是模块常量，来自中文重排项目的交付标准。但它同时改变了日译中的默认观感：深色背景上的白字会变成黑字。抹字后的底色通常是修复出来的背景色，深底黑字的可读性没有验证过。

**做法**：用一页深色背景加白字的真实样张验证。如果可读性有问题，把它做成设置项（默认值可以仍然是纯黑），而不是对所有场景强制。

### U7. README 面向的是开发者 —— 中优先，半天

**依据**【实测】：没有一张界面截图；FAQ 最后一条讲的是改 `core/manifest.py` 后要重新打包；"自己打包"的说明插在安装步骤中间；§1.2 列的几处过时信息。ROADMAP U5 要求"有截图、有该用哪个功能的决策指引"。

**做法**：README 只留用户路径（下载 → 首次运行 → 翻一本 → 校对 → 常见问题），开发内容移到 `docs/DEVELOPING.md` 或并入 HANDOFF。补 3 张截图（首次运行弹窗、翻译页、校对页）。英文版要么同步，要么缩成一段并指向中文版，不要维持一个内容过时的半成品。

### U8. 信任与分发 —— 低优先，记录在案

- 安装包未签名，Windows 会提示未知发布者（HANDOFF §6 已记）。代码签名证书有年费，在用户量起来之前不建议投入；在下载页和 README 写明"会看到这个提示、为什么、怎么核对 sha256"即可。
- 没有更新提示。ROADMAP §8 明确"不做在线更新"，但"启动时不联网"和"关于页放一个打开 Releases 页面的按钮"并不冲突，后者零成本。
- 下载页尚未上架（归 SUBLOG 仓库）。

### U9. 没有任何一个真实的陌生用户走过全程 —— 最重要的一条

ROADMAP U1 的验收方式是"找一个没用过的人实操，计时，记录他卡在哪"。到目前为止，首次运行弹窗的两轮修复（0.4.1、0.4.2）都来自作者或另一个会话的截图，HANDOFF §6 也记着"真实窗口里点「组件」页没有人工验收过"。上面 U1–U7 都是从代码和文档推出来的，**一次真人试用能直接告诉你哪几条是真问题、哪几条是我多虑**，比继续推演便宜得多。

## 4. 方向与路线

### 4.1 需要你拍板的三个决定

**D1. 「繁体中文 → 简体重排」要不要产品化？**

这是当前实际投入最多的方向，也是和已发布产品距离最远的部分。它依赖视觉模型读图、双模型交叉核对、人工看图裁决，流程文档 751 行。

- **选 A：保持为内部生产流程。** 只做 T1、T2 的收口，把通用脚本整理好，不进产品。代价最低。适合"这是我自己要用的批量加工线"。
- **选 B：把确定性的部分产品化。** 加一个「不翻译，只转简体并重排」模式：EasyOCR → `proofread` 规则 → `zhconv` → 重排。可以立刻复用现有流水线，但质量上限就是 OCR 的上限，AGENTS 第 30 条和 ROADMAP §5.1 都记录过这条路的正确率不够。**不建议。**
- **选 C：把视觉模型接进产品做 OCR 后端。** 质量最好，但要么联网调 API（打破"全部本地、无需 Key"的定位），要么本地跑 VLM（显存和下载量再加一档）。是一个独立的产品决策，不是顺手能做的事。

**我的建议是 A**，同时把 C 作为一个明确的后续探索项记下来。理由：这条线的质量目前靠人工看图兜底，这个环节产品化不了；而日译中主线还有 U1–U5 这些投入小、见效直接的事没做。

**D2. ROADMAP 里的「分格 / 放大 / 墨水屏」还做不做？**

两个半月没有动工，期间优先级实际已经让位给分发和中文重排。建议把 ROADMAP 改写成和现实一致的版本：保留它的门禁表和工作循环（这两部分质量很高），把 R1 / R2 / R8 / R9 从主线移到"待定"，等有真实用户反馈说需要再启动。一份没人照着做的路线图会让接手的 AI 和人都做出错误判断。

**D3. 目标用户是谁？**

"自己用 + 顺便开源"和"让陌生人用起来"对应的优先级不同。前者 T 系列优先，U4、U7、U8 可以不做；后者 U9 应当排在所有事情前面。ROADMAP 开头写的目标是后者，但近期的投入方向是前者。

### 4.2 建议的执行顺序

假设 D1 选 A、D3 选"让陌生人用起来"。

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **P0 收口**（约 1 周） | T1 提交在途改动、T2 清理脚本、T3 发 0.4.3、§1.2 文档修正、T10 依赖缺口 | `git status` 干净；门禁三绿；Release 上有 0.4.3；HANDOFF 的测试数字与实测一致 |
| **P1 保护**（约 1 周） | T4 golden_run、T9 慢测试、T11 CI、T8 schema 版本 | mock 版 golden_run 进门禁；pytest 回到 2 分钟以内；推送自动跑检查 |
| **P2 首次体验**（约 2 周） | **U9 真人试用一次**，再按结果做 U1 设置合并、U2 试跑前 3 页、U3 显存预检、U7 README | 一个没用过的人从下载到第一个成品的计时记录；U3 的报错有前后对比 |
| **P3 结构**（约 1 周） | T5 拆 `main_window.py`、T6 引擎清册，在 golden_run 保护下进行 | 单文件 ≤ 600 行；golden_run 前后一致 |
| **P4 补能力**（按需） | U5 译名表入界面、拖拽、增量导出；U4 小模型档位；U6 黑字开关；T7 阶段间释放 | 每项各自带实测数字 |

P2 排在 P3 前面是有意的：结构债不影响用户，而首次体验的问题会直接决定有没有人留下来。但 P1 必须在 P3 之前，这一点和 ROADMAP 原来的判断一致。

### 4.3 这次不建议做的事

- **不重写流水线为逐页全流程**。收益（实时出图）可以用「试跑前 3 页」拿到大部分，代价是 12 GB 卡上显存不够。
- **不做插件化、多后端抽象、在线更新、遥测**。沿用 ROADMAP §8 的判断。
- **不做 UI 自动化测试**。项目有实测过的崩溃理由，回归保护走 Qt-free 的 golden_run。
- **不给一次性脚本补测试或做通用化**，除非同一个动作已经重复写了三次以上。
- **不买代码签名证书**，在有稳定用户之前。
- **不动「变更治理」里的锁定参数**。本次评估没有发现需要调整它们的证据。
